# Phase 5B — Coordinate review and geometry preparation

**Status:** Tooling and review queue only. No production database writes, no stop acceptance, no route activation.

## Objective

Turn the Phase 5 candidate coordinate inventory into a human-reviewable stop-location register before any road routing is attempted. The source coordinate set is a 2024 secondary research dataset (Habib University / Data Research Lab Pakistan, CC BY 4.0); it is not a current operator GPS feed.

## Added tool

Run from the repository root:

\`\`\`bash
python scripts/build_coordinate_review.py
\`\`\`

It reads the committed Phase 5 node audit, stop crosswalk, and historical edge CSVs. It writes four files to \`reports/phase5b/\`:

- \`coordinate_review_map.html\` — Leaflet map of all 572 nodes; red marks exact-name SMTA candidates; orange marks coordinate-collision nodes; blue marks other historical nodes. Popups show node ID, historical route labels, candidate route-stop references and collision group.
- \`coordinate_nodes.geojson\` — point-only GeoJSON in standard [longitude, latitude] order, retaining source node IDs, historical labels, collision groups and candidate references.
- \`stop_review_queue.csv\` — 191 SMTA route-stop rows with blank reviewer decision, reviewer, date, evidence and notes fields.
- \`coordinate_qa_report.json\` — reproducible counts, coordinate bounds, collision groups, reused candidate-node mappings and edge-reference checks.

The HTML map uses Leaflet 1.9.4 and OpenStreetMap tiles, so a network connection is required to display its basemap. GeoJSON, CSV and JSON outputs are generated locally without external requests.

The Karachi envelope is a coarse anomaly screen, not a boundary validation. Being inside it does not establish that a point is a bus stop.

## Reviewer decision protocol

For each row in \`stop_review_queue.csv\`, choose exactly one:

- \`accept_candidate\` — the named source stop and point are the same physical boarding location, supported by evidence.
- \`reject_candidate\` — wrong place, ambiguous identity or clearly incorrect point.
- \`needs_field_check\` — map evidence cannot establish the boarding location/road side.
- \`needs_better_source\` — source evidence is insufficient or contradictory.

Record reviewer, review date, evidence URL/reference and a concise reason. Do not accept a stop from name similarity alone. Verify the correct road side/platform, not merely the general landmark. Multiple routes may share a stop only when they use the same physical boarding point.

For unmatched rows, add a proposed coordinate only in a separate reviewed correction column/file, with source evidence and confidence. Never silently geocode a place name or overwrite the historical source coordinate.

## Geometry gate

Road-following route geometry is intentionally not generated by this tool. A route shape must not be built from straight lines between named places, or from a route planner's guessed snaps. Geometry work starts only after:

1. Forward and reverse ordered stop lists have operator/source confirmation.
2. Every stop used by the direction has a reviewed coordinate and physical boarding side.
3. Route variants, loops, one-way roads, flyovers and access restrictions are resolved.
4. A licensed road network/routing source and its attribution are recorded.
5. The derived route is visually reviewed against the source alignment and its length is compared with published distance.

The existing 1,415 historical edges represent named-node graph connections, not road-centreline polylines. They remain historical/unverified.

## Safety

This phase does not connect to MySQL, call a geocoder or routing service, mutate the source CSVs, change source verification states, or publish stops/routes. The review CSV is a working copy. Approval and any eventual import remain separate controlled steps.
